# Звіт про виконання gz12

**Проєкт:** Sneaker Store — REST API магазину спортивного взуття.  
**Основа:** власний проєкт із gz11.  
**Мета роботи:** доповнити backend до повного CRUD і реалізувати фільтрацію позицій каталогу за категорією.

## 1. Розширення репозиторію

В інтерфейс `SneakerRepository` додано два методи:

- `findByCategory(String category)` — пошук кросівок за категорією;
- `deleteById(Long id)` — видалення запису за ідентифікатором із поверненням ознаки успіху.

У `InMemorySneakerRepository` реалізовано фільтрацію за точним значенням категорії без урахування регістру. Результати додатково сортуються за `id`. Видалення виконується через `ConcurrentHashMap.remove`; метод повертає `false`, якщо запису не існувало.

## 2. Вхідний DTO

Створено `web/dto/SneakerRequest.java` — окремий `record` для тіла запиту на створення та повне оновлення.

DTO містить усі поля позиції каталогу, необхідні для формування доменного об'єкта: бренд, модель, розмір, ціну, колір, цільову аудиторію, категорію, матеріали, сезон, ознаку водонепроникності, URL зображень і опис. Поля `id` у DTO немає: ідентифікатор генерується на сервері під час створення.

## 3. Маппер і сервіс

У `SneakerMapper` додано `toDomain(SneakerRequest request)`, який перетворює вхідний DTO на доменну сутність без ідентифікатора.

Інтерфейс `SneakerService` та його реалізацію `SneakerServiceImpl` розширено методами:

- `findAll(String category)` — повертає весь каталог, якщо категорію не задано або вона порожня, і відфільтрований список в іншому разі;
- `create(SneakerRequest request)` — створює позицію та повертає детальний DTO;
- `update(Long id, SneakerRequest request)` — перевіряє наявність запису, зберігає оновлені дані з тим самим ID і повертає детальний DTO;
- `delete(Long id)` — видаляє запис; якщо його немає, кидає `SneakerNotFoundException`.

Таким чином, бізнес-логіка залишається в сервісному шарі, а контролер працює через інтерфейс сервісу.

## 4. REST-ендпоінти

Контролер `SneakerController` доповнено та оновлено:

| Метод | Шлях | Призначення | HTTP-статус |
|---|---|---|---|
| GET | `/api/sneakers` | Перелік карток каталогу | 200 |
| GET | `/api/sneakers/{id}` | Деталі однієї позиції | 200 або 404 |
| GET | `/api/sneakers?category={category}` | Фільтр за категорією | 200 |
| POST | `/api/sneakers` | Створення позиції з `SneakerRequest` | 201 |
| PUT | `/api/sneakers/{id}` | Повне оновлення позиції | 200 або 404 |
| DELETE | `/api/sneakers/{id}` | Видалення позиції | 204 або 404 |

Вхідні JSON-дані приймаються через `@RequestBody`, а необов'язковий фільтр — через `@RequestParam`. Для створення використовується `@ResponseStatus(HttpStatus.CREATED)`, для видалення повертається `ResponseEntity.noContent().build()`.

## 5. Обробка відсутнього ID

Для `GET /api/sneakers/{id}`, `PUT /api/sneakers/{id}` і `DELETE /api/sneakers/{id}` з неіснуючим ID повертається `404 Not Found` через наявний `SneakerNotFoundException`.

Для `PUT` спочатку перевіряється наявність запису, після чого створюється оновлений доменний об'єкт із початковим ID. Для `DELETE` перевіряється результат `repository.deleteById(id)`.

## 6. Оновлення прикладів запитів і тестів

Файл `requests.md` доповнено командами `curl` для всіх сценаріїв:

1. отримання всього каталогу;
2. отримання однієї позиції;
3. фільтрація за категорією;
4. створення через `POST`;
5. повне оновлення через `PUT`;
6. видалення через `DELETE`.

Також наведено запити для перевірки `404` та відповіді статичного SVG-ресурсу. Для `POST` і `PUT` наведено JSON без поля `id`.

`SneakerControllerTest` розширено інтеграційними сценаріями для фільтрації (з перевіркою нечутливості до регістру), створення зі статусом `201`, оновлення зі збереженням ID, видалення зі статусом `204`, а також `404` для оновлення, видалення та читання неіснуючого запису. Перевірки створення/оновлення/видалення прибирають тестові записи після виконання.

- [x] Збережено шари `domain`, `repository`, `service`, `web` та інтерфейси між шарами.
- [x] Додано фільтр за полем `category` через `@RequestParam`.
- [x] Додано окремий `SneakerRequest` без `id`.
- [x] Додано перетворення `SneakerRequest` у доменну модель.
- [x] Реалізовано створення `POST` зі статусом `201 Created`.
- [x] Реалізовано повне оновлення `PUT` зі статусом `200 OK` або `404 Not Found`.
- [x] Реалізовано видалення `DELETE` зі статусом `204 No Content` або `404 Not Found`.
- [x] Збережено обидва GET-ендпоінти з gz11.
- [x] Оновлено `requests.md` прикладами всіх шести сценаріїв API.
- [x] Додано інтеграційні тести для CRUD та фільтрації.

**Примітка:** застосунок використовує in-memory сховище, як і в gz11. Створені, оновлені та видалені записи існують лише протягом поточного запуску застосунку; після перезапуску `SneakerSeeder` знову додає п'ять початкових позицій. Перевірка виконання Maven-тестів у середовищі підготовки архіву не була доступна, тому звіт фіксує реалізовані зміни та додані тести, а не стверджує, що тестовий запуск пройшов успішно.
